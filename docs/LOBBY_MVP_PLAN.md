## 10. 저장 [확정 + 기술 설계]

- 키 `ninefold-veil-save`, 버전 1. 구조: 재화(엽전, 이름 조각), 통계(출정 수, 일반/보스 처치 합계, 최고 생존 시간), 업그레이드 레벨, 도감 처치 수, 업적 수령 여부.
- 불러오기: 없거나 손상되면 기본값으로 시작. 손상 원본은 가능하면 백업 키에 보관.
- 초기화: UI에서 반드시 확인 후 실행. 가져오기: 형식 검증 → 확인 → 덮어쓰기. 검증 실패 데이터는 저장소를 건드리지 않음.
- 저장 실패(용량, 시크릿 모드, 차단): 예외를 잡아서 메모리에 보관하고 게임은 계속. UI에 "저장 안 됨" 표시는 M8에서.

## 11. 기술 위험과 개선안

**`game.js` 생명주기 문제 (가장 큰 위험)**: `startGame`이 `window` 이벤트 리스너와 `requestAnimationFrame` 루프를 등록하지만 끌 방법이 없음. 로비에서 전투를 여러 번 시작하면 리스너와 루프가 중복됨.

개선안 (M2, 최소 변경):
1. `startGame`이 `{ start(options), destroy(), getResult() }` 핸들을 반환한다. 반환값을 쓰지 않는 기존 `main.js` 호출은 그대로 동작한다.
2. 모든 `addEventListener`에 `AbortController`의 `signal`을 붙여서 `destroy()` 한 번으로 한꺼번에 해제한다.
3. `requestAnimationFrame` 번호를 저장하고 `destroy()`에서 `cancelAnimationFrame`, `ResizeObserver.disconnect()`를 호출한다.
4. 전투 종료(gameover/victory) 시 `onRunEnd({ result, survivalSeconds, normalKills, bossKills, dungeonId })` 콜백을 한 번만 호출한다.
5. 기존 Enter 재시작 동작은 단독 실행 모드(콜백이 없을 때)에서 그대로 유지하여 203개 기존 테스트를 보호한다.

## 12. 모바일 조작 (M9) [확정: 범위 포함]

- 가로 화면 기준. 좌하단 가상 조이스틱(8방향, 정규화), 우하단 대시 버튼.
- 자동 공격은 기존 시스템을 그대로 사용한다.
- 현재 게임에는 능동 스킬이 없고 대시만 있으므로 **스킬 버튼은 만들지 않는다**. 대시가 회피 역할을 한다.
- 포인터 ID 추적, 멈춤/사망/블러 시 입력 초기화, safe-area 대응, 리스너 해제를 포함한다.
- Phaser와 다른 엔진은 사용하지 않는다. 기존 키보드 조작은 유지한다.
- 구현 기준은 사용자가 준 "Mobile Controls Implementation" 프롬프트 전문이다(2026-10-27 두 번째 전달본). 핵심 제약: Phaser 및 다른 엔진 금지, 새 의존성 없음, 기존 PC 조작과 전투 로직 보존, 시각 에셋 생성 금지(코드/CSS 도형만).
- 입력 장치 처리와 게임 규칙을 분리한다. 터치 입력은 기존 키보드가 쓰는 이동/대시 경로에 합류시키고 전투 규칙을 복제하지 않는다.
- 스킬 버튼: 능동 스킬이 없으므로 만들지 않는다(사용자 승인, 2026-10-27). 프롬프트의 "실제 존재하는 스킬만 연결" 규칙에 따른다.
- 대시 버튼: 기존 대시(쿨다운, 대시 무적)를 그대로 호출하고, 누르고 있어도 반복 발동하지 않게 한다. 쿨다운 표시를 포함한다.
- 멈춤, 레벨업/보상 화면, 게임 오버, 창 포커스 상실, 화면 크기 변경, 터치 취소 시 조이스틱 값을 0으로 되돌린다. 보상 화면 중에는 카드 터치 선택만 받는다(현재 카드 클릭은 캔버스 click이라 터치에서도 동작하는지 M9에서 확인).
- 가로 화면, safe-area(`env(safe-area-inset-*)`), 중앙 전투 영역을 가리지 않는 배치.
- 인수 기준(프롬프트 6절): 개발 서버 실행, 프로덕션 빌드 성공, 키보드 이동 유지, 8방향 조이스틱, 놓기/취소 시 정지, 다중 터치 충돌 없음, 기존 공격 시스템 사용, 메뉴/정지 중 입력 차단, 여러 화면 크기, 재시작 반복 시 리스너 누적 없음, Phaser 없음.
- 보고 규칙: 자동 검증과 실기기 수동 검증을 구분하며, 실제 폰에서 테스트하지 않았다면 그렇게 적는다.
- 순서 의존: 리스너 해제와 재시작 안전성은 M2의 `destroy()`(11절)가 먼저 있어야 완전히 검증할 수 있다.
